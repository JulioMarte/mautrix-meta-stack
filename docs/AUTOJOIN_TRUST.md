# Meta portal auto-join trust model

The integration must not infer portal ownership from a hard-coded MXID prefix or from the current room name.

The authoritative trust boundary is the installed Matrix application-service registration generated by mautrix-meta:

- `sender_localpart` identifies the application-service bot user.
- `namespaces.users` lists user-ID namespaces the application service is interested in.
- Only `exclusive: true` user namespaces are treated as bridge-controlled ghost identities for automatic room joins. A non-exclusive namespace is only an interest declaration and does not prove ownership.

This follows the Matrix Application Service API contract and mautrix's generated registration model. The configured mautrix `username_template` determines remote-user ghost MXIDs and the registration represents the corresponding homeserver ownership boundary.

Runtime policy:

1. Read and YAML-parse the installed mautrix-meta `registration.yaml`.
2. Trust the bot derived from `sender_localpart` for the local Matrix server.
3. Trust an inviter matching any **exclusive** `namespaces.users[].regex` entry, but only when the inviter belongs to the local Matrix server.
4. Fail closed if the registration is missing, malformed, or contains an invalid regex.
5. Never trust an MXID merely because it starts with `@meta_`.
6. After requesting `/join`, verify the admin's `m.room.member` state actually becomes `join` before importing history or forwarding data to Chatwoot.

The registration file is mounted read-only into the integration container, so this policy automatically follows future mautrix-meta-generated ghost namespace changes after a valid registration regeneration/redeploy instead of requiring code changes for each ghost naming convention.
